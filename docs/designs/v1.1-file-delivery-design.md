# AstrBot SUSTech CLI 插件 v1.1 设计：聊天内文件投递

## 1. 文档信息

- **插件名称**：`astrbot_plugin_sustech_cli`
- **设计版本**：v1.2
- **前置版本**：v1（见 [`v1-design.md`](v1-design.md)）
- **设计状态**：已实现（v1.2.0）
- **目标平台**：QQ 官方机器人（`qqofficial` 适配器）、WebChat（`webchat` 适配器）

## 2. 背景与目标

v1 中 `/sustech-download` 与 `/sustech-calendar-export` 成功后只回复纯文本（文件名、大小、SHA-256），文件仅落盘在 `download_root` 内，用户无法在聊天中直接取得文件。

v1.1 目标：文件产出成功后，在同一条回复中以 `File` 消息段附带文件本体，用户在 QQ 官方机器人和 WebChat 中可直接下载。

本版本**明确不实现**：

- NapCat / aiocqhttp（QQ 个人号）适配。该链路涉及 `file:` URI 由协议端解析、跨容器共享挂载或 `callback_api_base` 文件服务，拓扑复杂，单独评估；
- gewechat（个人微信）。其适配器没有 `File` 分支，消息段会被静默丢弃；
- Telegram、飞书、企业微信、钉钉等其他平台的主动适配与验收（代码路径天然兼容，但不在本版本验收范围内，按"未知平台"降级处理）；
- AstrBot OpenAPI 附件上传（`POST /api/v1/file`）链路。文件就在本容器内，无需 HTTP 中转。

## 3. 方案选择

### 3.1 选定方案：容器内本地路径 + `Comp.File`

```text
用户 → /sustech-download ...
     → runner.download_attachment()  → 文件写入 download_root（v1 已有）
     → 构造 MessageChain [Plain(摘要), File(name, file=容器内绝对路径)]
     → yield event.chain_result(chain)
     → 适配器读取文件并上传（qqofficial: base64 上传媒体 API；webchat: 复制到附件目录）
```

选择理由：

1. 文件本来就由插件进程写入本容器文件系统，`Comp.File` 的 `os.path.exists` 检查直接通过；
2. `qqofficial` 与 `webchat` 适配器都是 AstrBot 进程自己读文件再上传/复制，与协议端部署位置无关，**不需要共享 volume、不需要 `callback_api_base`**；
3. 不引入新依赖、新配置服务或 HTTP 中转。

### 3.2 否决方案

| 方案 | 否决原因 |
| --- | --- |
| 共享 volume + 协议端直读 | 仅 aiocqhttp 链路需要；本版本不做 NapCat |
| `callback_api_base` 文件服务 | 引入公网回调地址配置，仅服务 aiocqhttp 跨容器场景 |
| OpenAPI `attachment_id` 上传 | 两次 HTTP 往返 + API Key 管理，文件在本容器时无收益 |

## 4. 功能范围

### 4.1 受影响的命令

| 命令 | 变更 |
| --- | --- |
| `/sustech-download` | 成功后回复 `[Plain(下载摘要), File(文件)]` 消息链 |
| `/sustech-calendar-export` | 成功后回复 `[Plain(导出摘要), File(ics 文件)]` 消息链 |

其余命令（查询类、提交类）不变。

### 4.2 LLM Tools（v1.2 更新）

`filter.llm_tool` handler 只能返回 `str` 给模型，无法携带消息链。v1.2 采用旁路投递：工具成功产出文件后，复用 `prepare_file_delivery` 门控，通过 `context.send_message(event.unified_msg_origin, chain)` 把 `[Plain(文件名), File(文件)]` 主动发到当前会话；工具返回文本明确告知模型"文件已作为附件发送"或"平台不支持，文件已保存到受控目录"，防止模型对用户作出错误陈述。

- 投递失败（平台不支持主动消息、平台侧拒绝等）不抛出，回退文本摘要；
- QQ 官方接口的主动消息受平台配额/窗口限制，失败按降级处理，不因此判定下载失败；
- `sustech_prepare_assignment_submission` 不变：仍只生成预览，提交必须显式 `/sustech-submit-confirm`。

### 4.3 平台门控

仅以下平台发送 `File` 段，其余平台降级为 v1 的纯文本回复：

| 平台 | 适配器 | 行为 |
| --- | --- | --- |
| QQ 官方机器人 | `qqofficial` | 发送 `File` 段（适配器读文件 base64 上传媒体 API） |
| WebChat | `webchat` | 发送 `File` 段（适配器复制到附件目录，前端可下载） |
| 其他/未知 | 任意 | 回退纯文本（v1 行为，不报错） |

门控基于 `event.get_platform_name()`（或等价平台标识）与白名单比对，白名单来自配置（见 §5.3），默认 `["qqofficial", "webchat"]`。

## 5. 详细设计

### 5.1 文件路径解析

`runner` 的下载/导出结果已包含 `result["file"] = {name, rel_path, size, sha256}`（`ProducedFile`，相对 `download_root`）。投递路径：

```python
abs_path = Path(download_root).resolve() / result["file"]["rel_path"]
```

约束：

1. 必须使用 `_finalize_output` 之后的最终 `rel_path`（`download_attachment` 可能因真实文件名重命名，`runner.py` 中二次 finalize 后的结果才是最终路径）；
2. `download_root` 配置建议写绝对路径（Docker 官方镜像中为 `/AstrBot/data/sustech-cli/files`）。相对路径按 AstrBot 进程 cwd 解析，本版本不做强制，但文档与配置模板推荐绝对路径；
3. 构造 `Comp.File(name=result["file"]["name"], file=str(abs_path))`。`name` 已经是 `sanitize_filename` 处理过的安全文件名。

### 5.2 消息链构造

```python
import astrbot.api.message_components as Comp

chain = [
    Comp.Plain(formatter.format_download_result(result["file"])),
    Comp.File(name=result["file"]["name"], file=str(abs_path)),
]
yield event.chain_result(chain)
```

- 摘要文本保留（大小、SHA-256 仍是用户校验依据）；
- `File` 段放最后，避免部分适配器对富媒体后续段落的处理差异；
- 不引用、不 At 发送者，保持与 v1 回复风格一致。

### 5.3 配置项

`_conf_schema.json` 新增：

| 配置项 | 类型 | 默认值 | 说明 |
| --- | --- | --- | --- |
| `send_file_in_chat` | bool | `true` | 文件产出成功后是否随回复投递文件本体 |
| `file_message_platforms` | list[string] | `["qqofficial", "webchat"]` | 允许投递 `File` 段的平台白名单 |

`send_file_in_chat=false` 或平台不在白名单时，行为与 v1 完全一致。

### 5.4 插件侧改动点

- `main.py::sustech_download`：成功后按 §5.1–5.3 构造消息链；
- `main.py::sustech_calendar_export`：同上；
- `main.py` 新增内部助手：`_file_delivery_chain(event, result) -> list | None`，集中实现门控、路径拼接、降级判断，返回 `None` 表示回退纯文本；
- `runner.py` 不改；`formatter.py` 不改。

## 6. 安全模型

沿用 v1 安全模型，新增约束：

1. **只投递 runner 产出的文件**：`File` 段的 `file` 必须来自 `_finalize_output` 校验过的 `rel_path`，已保证位于 `download_root` 内、经符号链接检查、大小不超过 `max_download_bytes`。不接受任何用户输入路径；
2. **访问控制不变**：文件投递发生在 `_access_file` 通过之后，与 v1 下载命令同一权限边界（`private_only` + `allowed_users`）；
3. **文件名安全**：`name` 来自 `sanitize_filename`，不含路径分隔符与控制字符；
4. **大小限制**：`max_download_bytes`（默认 50 MiB）是唯一硬性上限。QQ 官方媒体 API 的实际文件大小上限未在本设计中验证，超出平台侧限制时按 §7 降级；
5. **凭证不外泄**：文件投递路径不经过 LLM 上下文，不改变主密码注入模型。

## 7. 错误处理与降级

| 场景 | 行为 |
| --- | --- |
| 平台不在白名单 / `send_file_in_chat=false` | 纯文本回复（v1 行为） |
| 产出文件在构造消息链前已不存在 | 记 warning，纯文本回复 |
| 适配器发送 `File` 段抛异常（如平台侧超限） | 记 exception，补发纯文本回复，不让 handler 崩溃 |
| 文件下载本身失败 | 维持 v1 错误文案，不进入投递逻辑 |

降级后用户至少拿到文件名、大小、SHA-256 与受控目录相对路径，可从宿主机挂载目录取文件。

## 8. 测试与验收

### 8.1 单元测试（`tests/`，标准库 unittest）

1. 白名单内平台 → `_file_delivery_chain` 返回含 `File` 段的消息链，路径为 `download_root/rel_path`；
2. 白名单外平台 / 开关关闭 / 文件缺失 → 返回 `None`；
3. `rel_path` 使用重命名后的最终值（模拟 CLI 返回真实文件名场景）。

### 8.2 手动验收

Docker 部署（`-v $PWD/data:/AstrBot/data`，`download_root=/AstrBot/data/sustech-cli/files`）：

1. WebChat：执行 `/sustech-download`，聊天中出现可下载文件，内容与 `data/sustech-cli/files/download/...` 一致；
2. QQ 官方机器人：执行 `/sustech-download` 与 `/sustech-calendar-export`，私聊中收到文件；
3. 负面：配置 `file_message_platforms: []` 后回复退化为纯文本；删除产出文件后回复纯文本且插件不崩溃。

## 9. 非目标

- NapCat/aiocqhttp 文件投递（含 `callback_api_base`、共享挂载方案）；
- gewechat 及文档适配矩阵中未列平台的适配；
- 文件过期清理策略（沿用 v1：不自动清理，由部署方管理 `download_root`）；
- 断点续传、分片上传、进度展示。
